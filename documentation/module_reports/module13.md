# Module 13 — Workout Plan Module (Exercise Library, Weekly Schedule Display)

**Status:** Complete
**Branch:** `feature/module-13-workout-plans` → `dev`

## Scope, following Module 12's established pattern

Same audit approach as Module 12: before writing code, confirmed what already existed for workouts.
`workout_recommendation_records` (Module 11's live KNN candidate data) already had every scalar
field displayed on the `/meal-plan` page except IDs and profile-redundant fields (age/gender/
fitness_level) — so there were no unshown backend fields to surface. The legacy `workout_plans`
table (Module 2) has a `weekly_schedule` string column, but it's dead: `image_analysis_service.
analyze()` has never written to it since Module 11, same status as `meal_plans` (Module 12 already
declined to build detail pages for these). No exercise/workout reference dataset existed anywhere in
the repo — unlike `sri_lankan_foods` before Module 12, this wasn't even a placeholder.

**Key finding: a real "weekly schedule" isn't possible from any existing data.**
`workout_recommendation_records` only has a `days_per_week` integer count — no field anywhere (live
or legacy) says *which* days, let alone what exercise happens on which day. Rather than either (a)
skip the roadmap item, or (b) fabricate a specific day-by-exercise assignment that isn't in the data,
this module builds a **deterministic, explicitly-labeled suggestion**: `days_per_week` spread evenly
across a 7-day grid (e.g. 3/week → Mon/Wed/Fri, 5/week → Mon/Tue/Wed/Fri/Sat), shown with a caption
stating it's a suggested spread, not sourced data, with a link to the new exercise library so users
can choose what to actually do each day.

## What was built

### Pre-existing infra gotcha, caught before it recurred
Generating this module's migration reconfirmed something noted in Module 11: this MySQL server's
`default_storage_engine` is still `MyISAM` (server-level setting, never changed — Module 11 only
converted *existing* tables to InnoDB). The autogenerated migration for the new `exercises` table
did **not** include `mysql_engine='InnoDB'`, which would have silently created another broken
MyISAM table. Caught by checking `SHOW VARIABLES LIKE 'default_storage_engine'` before applying;
fixed by adding the kwarg to `op.create_table(...)` before running `flask db upgrade`. Documented as
a standing heads-up in `CLAUDE.md` so future modules check this on every new migration until the
server config itself is fixed (a bigger change, out of scope here — see Module 11's report for why
it wasn't done at the server level).

### Real dataset (Kaggle, per CLAUDE.md rule 6)
`prajwaldongre/best-50-exercise-for-your-body` (CC0-1.0) — 50 real exercises with sets/reps,
calories burned, target muscle group, equipment, difficulty level, and a short benefit description.
No duplicates, no nulls except `equipment` (bodyweight exercises legitimately have none, same pattern
as Module 11's workout dataset). Committed to `datasets/workouts/Top50ExercisesForYourBody.csv`.

### Database (`backend/app/models/exercise.py`, migration `f2895c49193b`)
New `exercises` table: `exercise_id, exercise_name, target_muscle, difficulty, equipment (nullable),
sets, reps, calories_per_30min, benefit`. Standalone — no FK to anything else, unrelated to the
Module 11 recommendation pipeline.

### Data loading (`backend/app/seed_exercise_data.py`)
`load_exercise_records()` parses the CSV directly (mirrors `seed_food_data.py`'s pattern); `seed.py`
gained `_seed_exercises()`, idempotent by `exercise_name`, called from `seed_data()`. Verified:
seeded twice, 50 rows both times.

### Backend API (`backend/app/routes/exercises.py`, public — no auth, matches the pre-existing
`/workouts` public nav item since Module 5)
- `GET /api/v1/exercises?difficulty=&q=` — list with difficulty filter + name search.
- `GET /api/v1/exercises/difficulties` — distinct difficulty levels for a filter dropdown.
- `GET /api/v1/exercises/:id` — full detail (404 via the `NotFoundError` added in Module 12).
- New `exercise_repository.py`/`exercise_service.py`/`exercise_controller.py`/`exercise_schema.py`,
  registered as `exercises_bp`.

### Frontend
- **`Workouts.jsx`** (`/workouts`, replaces the Module 5 `ComingSoon` stub) — same shape as Module
  12's Healthy Foods page: debounced search + difficulty dropdown, a table of matching exercises,
  click a row for a detail modal (benefit, target muscle, sets x reps, calories, equipment).
- **`weeklySchedule.js`** — pure function `getSuggestedWorkoutDays(daysPerWeek)`, spreads N days
  evenly across Mon-Sun using `Math.floor((i * 7) / n)`; verified for every n from 1-7 (3 → classic
  Mon/Wed/Fri, 7 → every day, always exactly N unique days).
- **`MealPlanDetail.jsx`** — workout card gained a 7-day pill row (highlighted = suggested workout
  day) under a "Suggested weekly schedule (N days/week)" heading, with the honesty caption described
  above and a link to `/workouts`.
- `ComingSoon.jsx` deleted — after this module, nothing references it (Module 12 already replaced
  its `/healthy-foods` usage; this was its last caller).

## How to test locally

**Backend**
```
cd backend
pytest              # 75 passed
flake8 .            # clean
flask db upgrade    # applies the exercises table migration (InnoDB)
flask seed          # loads the real 50-row exercise dataset (idempotent)
flask run
curl "localhost:5000/api/v1/exercises?difficulty=Beginner"
curl "localhost:5000/api/v1/exercises/difficulties"
```

**Frontend**
```
cd frontend
npm run lint     # 0 errors, 1 pre-existing benign warning
npm run build    # succeeds
npm run dev      # visit /workouts (no login needed), or log in and visit /meal-plan for the schedule
```

## Deferred / known limitations

- The weekly schedule is a derived suggestion, not per-day-specific exercise assignments — no data
  source (live or legacy) has that information; see the scope section above.
- `workout_plans` (legacy Module 2 template table, including its unused `weekly_schedule` column)
  remains in the schema, unused, same status noted in Module 11/12's reports.
- `exercises` has no admin-facing edit UI yet — Module 14 (admin panel) is the natural home, same
  as noted for `sri_lankan_foods` in Module 12.
- The `default_storage_engine = MyISAM` server setting itself is still not fixed — every future
  migration needs the explicit `mysql_engine='InnoDB'` workaround (see the standing heads-up added
  to `CLAUDE.md`).
